# South-polar terrain screening: provenance and limits

The default optional terrain screen uses `dem_400m.bin.gz` (SHA-256 `71d285a32a4c1410ffed5c4d8bc62ea8ed04625f443d6f72997fa5d8b0208dbf`), from the MIT-licensed [Lunar Horizon / CLPS-MOON-BROWSER](https://github.com/localizedprojects/CLPS-MOON-BROWSER/tree/9801046af387d40cc77db4f0557c802ad8cee5b4/app/assets/data/map) project, commit `9801046af387d40cc77db4f0557c802ad8cee5b4`. Its license is included in `UPSTREAM_LICENSE.txt`; its unmodified map metadata is `upstream-map.json`. The project attributes the grid to NASA LRO LOLA PDS products [LDEM_80S_80M](https://pds-geosciences.wustl.edu/lro/lro-l-lola-3-rdr-v1/lrolol_1xxx/data/lola_gdr/polar/img/ldem_80s_80m.img) and [LDEM_75S_120M](https://pds-geosciences.wustl.edu/lro/lro-l-lola-3-rdr-v1/lrolol_1xxx/data/lola_gdr/polar/img/ldem_75s_120m.img); see NASA's [LOLA GDR data set description](https://pds.nasa.gov/ds-view/pds/viewProfile.jsp?dsid=LRO-L-LOLA-4-GDR-V1.0). The inner grid is a 5 × 5 block mean of 80 m data and the outer ring is an area-weighted average of 120 m data, both rounded to metres. We independently downloaded both original NASA rasters and compared their full grids with the derivative as described below; the source images were not added to the repository. The derivative hash checks integrity, not scientific correctness. These are gridded, interpolated historical measurements, not live terrain or an unaltered NASA product. The LOLA data do not measure every pixel. The 400 m averaging suppresses smaller features; do not confuse grid spacing with actual spatial accuracy.

## Method

The 2280 × 2280 grid is int16 elevations in metres above a 1737.4 km sphere, south-polar stereographic, south pole centered, 0°E up, 90°E right, mean-Earth / DE421 frame according to the upstream metadata. 400 m cells are sampled bilinearly, with pixel-center registration. Site latitude is planetocentric, longitude east-positive; inputs are restricted to 80–90°S, where every ray starts inside the raster. A site ground height is interpolated; observer height is **above that estimated terrain**, not above the reference sphere. A great-circle radial ray samples every 100 m from 600 m to 300 km or the raster edge, whichever comes first, for each integer azimuth; the highest point angle is computed with spherical curvature. The nearest 600 m is omitted because the grid cannot resolve it and bilinear near-field dips can produce spurious horizons. Directions between sampled azimuths are linearly interpolated; sharp terrain can be missed. The compressed raster is checked via a pinned checksum when loaded, then retained in process memory; a corrupt or missing file fails closed, rather than reverting to a flat horizon. There is no coverage or uncertainty raster and no extrapolation outside the grid.

`POST /api/terrain-screen` compares geometric Sun/Earth **centers** at requested 15/30/60-minute bin midpoints, using the terrain ground elevation plus observer height in the Step 1 geometric ephemeris. It returns the profile, per-bin directions, results, hashes and assumptions. It does not apply the main comparison's fixed clearances. An `above_sampled` result **does not establish actual visibility**: near-field obstacles, terrain beyond each ray’s sampled endpoint, averaging, DEM errors, interpolation, angular and temporal undersampling and obstructions between sampled rays may matter. A below-sampled result is also model-dependent, not a certified blockage. The Sun and Earth are not disks; there are no terrain uncertainty bounds, eclipse, antenna or operations constraints. No hardware or power model is included. Bins can miss events. This is exploratory and not for mission or safety decisions.

## Cross-checks (not an independent scientific audit)

The third-party project's independently written Dart/Python raster tests supply the `coarseHorizon` subsection of `tests/upstream_coarse_horizon_reference.json`, reproduced from its `app/test/fixtures/spice_truth.json` at the above commit under the accompanying MIT license. Our decoder matches its full-grid integer sum `-6964042991` and five reference pixel values. Site ground heights agree to within 1e-6 m for three fixture sites. In 540 common 2° azimuths for 2 m observers at (-89.4679°, -137.411°), (-85.98°, -0.26°), (-80.13°, 1.44°), mean absolute horizon differences are 0.001213°, 0.000268°, 0.000074°; maxima are 0.01112°, 0.00651°, 0.00280° respectively. The upstream calculation uses a different, variable radial sampling scheme extending to 300 km and can omit samples outside the raster; ours stops when a ray leaves the grid. Thus the differences are expected and quantify the substantial effect of assumptions, not a global accuracy bound. Both use the same 400 m derivative and related geometry; this is an independent implementation cross-check, **not** verification against NASA original data, independent observational truth, or an expert audit. Tests also exercise analytic flat-sphere and raised-observer cases, circular azimuth, missing/corrupt data and API input limits.


## Source verification against the two NASA PDS rasters

On 2026-11-14, both original NASA PDS products were downloaded to a GitHub-hosted runner, whose [check annotations](https://github.com/hariszafar740-lang/hariszafar740-lang/actions/runs/43594580386) record the results. [LDEM_80S_80M.IMG](https://pds-geosciences.wustl.edu/lro/lro-l-lola-3-rdr-v1/lrolol_1xxx/data/lola_gdr/polar/img/ldem_80s_80m.img) is 115,520,000 bytes, SHA-256 `e6591eeea35402ca5e124ca00f5bf0774381a2d4fa919144b455d82b8ff65fdc`; [LDEM_75S_120M.IMG](https://pds-geosciences.wustl.edu/lro/lro-l-lola-3-rdr-v1/lrolol_1xxx/data/lola_gdr/polar/img/ldem_75s_120m.img) is 116,250,752 bytes, SHA-256 `ae3afc3c75c33d43666ca06c83ca08f0b12ef03b7d36d2d791d972730794391b`. The hashes also agree with the pinned upstream project's published hashes. The PDS labels ([80 m](https://pds-geosciences.wustl.edu/lro/lro-l-lola-3-rdr-v1/lrolol_1xxx/data/lola_gdr/polar/img/ldem_80s_80m.lbl), [120 m](https://pds-geosciences.wustl.edu/lro/lro-l-lola-3-rdr-v1/lrolol_1xxx/data/lola_gdr/polar/img/ldem_75s_120m.lbl)) describe little-endian signed 16-bit values, 0.5 m/DN, 1737.4 km sphere, planetocentric and east-positive coordinates, DE421 mean-Earth/polar-axis frame, pixel registration and polar stereographic projection. They describe gridded, interpolated historical measurements, not a direct measurement at every cell.

`scripts/validate_terrain_sources.py DIR` verifies both hashes and reconstructs source area averages using an independent integer-overlap calculation. The entire **2,310,400-cell inner block matched exactly**. Of **2,888,000 outer ring cells**, 1,558 differed by 1 m; every difference was an exact half-metre rounding tie in the integer reference, with no other mismatches and no fill sentinel in the source window. This is consistent with differing floating-point rounding at ties, but is not proof of the upstream implementation's exact rounding sequence. Neither file's physical accuracy, uncertainty or scientific fitness is established by hash or processing agreement. `numpy` is required only for these optional validation scripts, not normal app operation.

## Optional original-raster mode

The default remains the bundled 400 m derivative. An additional mode reads the verified **original 80 m and 120 m** PDS files. To install them separately from the project root (requires internet, about 232 MB of disk plus temporary download space, and ~232 MB of RAM per application process once loaded):

```sh
python scripts/fetch_native_lola.py "$HOME/lunaris-lola"
export LUNARIS_NATIVE_DEM_DIR="$HOME/lunaris-lola"
bash run.sh
```

Select “Original 80/120 m” in the terrain panel. Files are downloaded to temporary names, SHA-256/size checked and only then published; existing nonmatching files are never overwritten. Runtime checks both files before use and retains immutable bytes in memory. Restart after changing the directory/files; caches are per process. Missing, corrupt or sampled fill data fail closed with 503, never silently falling back to coarse results. There is no automatic network fetch on API requests. The native mode samples bilinearly on the 80 m raster where covered, otherwise the 120 m raster, at **40 m radial intervals**, 1° azimuth, from 600 m to 300 km or the source-raster edge. It remains a sampled approximation and does not use additional information below 600 m or beyond the cutoff. It can take substantially longer than the bundled mode.

## Original-resolution cross-check and sensitivities

`scripts/compare_terrain_high_resolution.py DIR OUTPUT.csv` independently computes spherical destination points and directly bilinearly samples native 80/120 m rasters at 40 m intervals for **33 selected rays** (three sites, eleven azimuths, 2 m above each raster's own ground). For a fair source comparison it stops at the bundled raster edge even when the original extends farther. Inputs and results are archived in `tests/pds_native_horizon_comparison.csv`. The coarse-minus-native horizon differences range from **−0.833693° to +0.321778°**; largest absolute difference **0.833693°**. Site elevations differ by up to about 4.84 m in these cases. These comparisons combine different source resolutions and ground heights, radial sampling and angular interpolation; they are not a global error estimate and do not cover omitted terrain. Some native peaks lie at the first 600 m sample, indicating that omitted nearer terrain could be important.

The new original-raster mode was separately run against the archived native reference at these cases: the [runner annotations](https://github.com/hariszafar740-lang/hariszafar740-lang/actions/runs/43594807375) report max ground difference **4.1e-7 m**, max integer-azimuth horizon difference **4.6e-10°** for 24 rays, and max half-degree direction difference **0.008418°** for nine rays (application interpolates its 1° azimuth profile). Three profiles including initial source load took about 15.9 s on that runner; this is not a performance guarantee. `scripts/check_native_horizon_regression.py` reproduces this check when the files are installed. The reference uses the same originals and comparable geometry, not a physical observation or external human review. Exact comparison tolerances are regression thresholds only.

The API now exports the sampled peak distance per integer azimuth and how many rays end at a raster edge before 300 km. Each bin also includes target-minus-interpolated-horizon margin and minimum coverage of its two neighboring rays. A ±1° horizon-offset experiment counts midpoint hours whose above/below classification changes; the offset is **illustrative**, not a measured uncertainty, a probability or bound. The 33-ray comparison itself demonstrates that even smaller offsets can be exceeded. The peak distance is a discrete sampled maximum, not a verified obstruction location. Neither mode supplies real visibility, a continuous skyline, measured DEM error, finite-disc effects, subpixel or near-field obstacles, terrain beyond coverage, a grazing-event search, or operational assurance. The screening relies on the still-unreviewed Step 1 ephemeris.

An independent human reviewer has **not** been identified, contacted or accepted this phase. `INDEPENDENT_TERRAIN_REVIEW.md` is an unsent request and review record. Phase 2 remains incomplete against that requirement; no independent 10/10 is claimed.
